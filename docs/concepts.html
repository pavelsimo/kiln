How kiln works

A software factory you install into your repo.

You hand kiln a task. It opens the issue, plans it, builds it in its own worktree, proves and reviews it, ships the pull request, and writes down what it learned so the next task starts warmer. This page explains the parts and the rules that hold them together. The /kiln-* commands run inside your coding agent (Claude Code, Codex, Cursor). Plain kiln … runs in a terminal.

§1 · Principles

What kiln believes

Ten rules shape everything else on this page. Several come from Cursor's pstack, and kiln adds a work queue built on issues, labels and acceptance criteria, plus project memory that lives in the repo. The label on the left says where each idea comes from.

kiln

The issue is the unit of work

Every task becomes a GitHub issue with acceptance criteria before any code. One issue, one branch, one worktree, one PR that says Closes #N.

pstack

One door in

/kiln is the router. It restates the goal, sizes it, and picks a playbook. Action skills are explicit tools that never fire by accident.

pstack

The playbook becomes the todo list

The router copies the playbook's steps into the agent's todo list word for word. A skipped step stays visible as skip: <reason>.

kiln

Memory is a file you can review

Project memory lives in .kiln/memory/, is committed with the work, and shows up in PR diffs. It does not depend on any agent's transcript format.

kiln

One writer per file

Each memory file has exactly one skill allowed to write it. Parallel worktrees never edit the same file, so memory never causes a merge conflict.

pstack

Evidence over assertion

A review finding counts only if it points at a command that reproduces it. Rigor scales with task size, so small fixes stay cheap.

pstack

Prove it on the real surface

Done means every acceptance criterion was checked on the thing it describes: the running app, the real command, a value read back. A green build is not proof. When something can't be checked, kiln reports INCONCLUSIVE, never a pass (§8).

kiln

Autonomy is a setting. Safety is not.

How often kiln stops for you is set in config. Force-pushing shared branches, deleting work, and deploying always stop for you (§7).

pstack

Facts in code, judgment in skills

If git or gh can answer a question exactly, the kiln binary answers it, the same way every time, with no model involved. Skills run inside your coding agent and keep the work that needs reading code, running the app or making a call (§5).

kiln

Standalone

Everything kiln runs ships inside the binary. It never calls a skill or tool it didn't install. The ideas it borrows are rewritten as its own kiln-* skills (§14).

§4 · Issue states

Labels are the state machine

An issue's kiln:* label tells you where it is in the factory, so any person or agent can see the state on GitHub without asking kiln. Skills change it only through kiln move, which refuses any move the diagram doesn't allow and exits 3.

§5 · Code or agent

Facts in code, judgment in skills

Kiln has two kinds of parts, and every job belongs to exactly one. If git or gh can answer a question exactly, the kiln binary answers it: no model, same input, same output. If the job needs reading code, running the app, or deciding what is good enough, it is a skill, and it runs inside your coding agent.

Skills ask, never re-derive

A skill that needs a fact calls the binary with --json and uses the answer. It doesn't loop over gh pr checks and guess, so the answer can't change with the agent or the model.

The binary never judges

No model, no code edits, nothing but git, gh and files. If answering needs reading code or deciding what is good enough, it belongs in a skill.

Rules that must hold live in code

Labels move only along the state machine. kiln merge refuses red checks or a stale verdict, treats INCONCLUSIVE as not ready unless you accept it at ◆2, and pins the merge to the head commit it checked. An agent that talks itself into a merge still hits the binary.

Exit codes

Every kiln command uses the same four codes, so a skill can branch on the answer without parsing text. Pass --json for machine output on stdout.

0ok, or the answer is yes
1git or gh failed, or a file couldn't be read
2bad usage: unknown flag or wrong arguments
3the answer is no: not ready, stale, illegal move, problems found

The playbook becomes the todo list

An idea from pstack. Before doing anything, the router copies the playbook's steps into the agent's todo list word for word. A step can't silently disappear, because skipping it means rewriting it in place as skip: <skill> · <reason>, and kiln-log records it under ## Skipped. You can audit a run by reading its list. Size L never skips the plan, whatever anyone asks.

§7 · Autonomy × rigor

How far kiln goes on its own

Two settings. autonomy in .kiln/config.yaml decides when kiln stops for you. The task's size label decides how hard kiln checks its own work, through rigor. Size L tasks raise the bar in every mode.

manual

Kiln runs one skill, reports the result, and suggests the next step. Nothing chains on its own. Good while you're getting to trust it.

stops · after every step

gated

default

Kiln runs the whole playbook and waits for you only at the gates listed in gates:, which by default are both: before writing code and before merging.

stops · ◆1 plan · ◆2 merge

autopilot

Kiln goes from task to merged PR as long as kiln ready passes: every predicate VERIFIED, CI green, review PASS. INCONCLUSIVE never merges on its own. Size L still stops at the plan, through rigor.L.force_gates.

stops · ◆1 for L tasks · hard stops
Always stops
  • force-push to a shared branch
  • delete unmerged work or data
  • deploy or release · ◆ before the tag
  • merge with failing checks
  • change secrets or repo settings
  • message people outside the repo
  • edit a path under “Do not touch without asking”

Retro and onboarding PRs also wait for your yes in every mode, because they change what every future task reads. The release gate (§11) is the “deploy or release” stop, so autopilot stops there too.

§8 · Verification

Proven on the real surface

kiln-verify is a skill, not a command. Proving a change means reading the code, running the app and judging what came back, and only a coding agent can do that. The binary supplies the facts around it: which standing checks apply, and whether a verdict is still fresh. The rules are adapted from pstack's prove and verifier skills, rewritten as kiln's own.

What to checkthe issue

Each acceptance criterion is a predicate, P1…Pn: an outcome that can pass or fail. kiln-issue rewrites anything unobservable (“feels faster”) or asks, and adds at least one “must not change”. You see them at ◆1, before any code, and they are never loosened later to make a check pass. Standing checks join them as C1…Cn when kiln checks matches the branch.

When it counts as provenkiln-verify

Check the surface that changed, not a proxy. Climb the evidence ladder. Audit every test used as evidence. Give each predicate one verdict. The overall verdict is the weakest one, and INCONCLUSIVE is not a pass.

VERIFIEDNOT VERIFIEDINCONCLUSIVE

How to run the app.kiln/verify/

DRIVER.md says how to launch, health-check, drive, capture evidence and clean up. The feature map in features/ says how a user reaches each feature. Neither holds a single pass or fail rule. kiln-verifier writes both and proves them with one full run.

A change that touches two surfaces needs a check on each. No driver yet and the check needs the running app? kiln-verify drives it by hand if it can, and otherwise marks the predicate INCONCLUSIVE and suggests kiln-verifier. It never swaps in a proxy.

The test audit

A test counts as evidence only if it calls the real code the way users do, asserts a literal expected value, and would fail if every import returned undefined. Tests that fail the audit are named in the report so they can be fixed.

Bug fixes, before and after

kiln-verify builds the old version in a throwaway worktree, sees the symptom twice there, then sees it gone twice on the new build, on the same surface. It names the root cause at a file:line. A fix that only hides the symptom (a nil check, a swallowed error, a retry) is NOT VERIFIED.

Who checks, by size

S the author. M a fresh-context checker that gets only the predicates, the diff and the driver. L a swarm at the merge-ready head: one lane reruns the gates, one proves the key behavior live, one audits the diff and the receipts. The live lane is the floor. Verdicts are tied to a SHA. kiln verdict keeps one only for the same commit, the same tree outside .kiln/memory/, or a clean rebase with the same git patch-id.

The driver's life

  1. Createkiln-onboard hands off to kiln-verifier create. It finds the run command, ready signal, drive mechanism and isolation in the repo, asks only what the code can't answer, writes DRIVER.md and 3 to 5 feature files, then proves them: launch, doctor, drive one feature, capture evidence, clean up.
  2. Usekiln-verify follows DRIVER.md whenever a predicate needs the running app, and saves evidence where it says.
  3. Notice driftEach feature file lists the source globs behind it. kiln doctor counts commits that touched them since the driver last changed. That's a fact, so it's code.
  4. MaintainWhen doctor says the driver is behind, kiln-retro runs kiln-verifier maintain: one reader per feature against the source, then one live pass over every feature. Mismatches are sorted into doc drift, harness gap, product gap or unreachable. Only the map is fixed. Product gaps become issues. At most one PR, and the <!-- maintained … --> line at the end of DRIVER.md resets the drift count.
  5. GraduateA strong lesson that can be checked becomes a standing check in checks.yaml, through the same retro PR. It must run green on the default branch first. kiln-onboard seeds the first checks from path-scoped CI jobs.

§10 · Factory floor

Several firings at once

Each issue gets its own git worktree next to the repo, so up to max_in_flight tasks (3 by default) build in parallel without touching each other's files. Each worktree writes only its own task journal, which keeps memory free of merge conflicts.

kiln status reads open issues with kiln:* labels, open PRs and their checks, git worktree list and the task journals. No model is involved, so it gives the same answer in a plain terminal, in CI, or through /kiln-status, which runs kiln status --json and adds one suggestion per item waiting on you. §11 · Releases

Many firings, one tag

A release has no issue of its own. It gathers every task merged since the last tag. kiln-release works from the squash commits already on main, writes CHANGELOG.md once, lands it through a normal PR, and tags the merge commit. Everything before the tag can be undone by closing that PR.

  1. PreflightFresh default branch with tags fetched, clean tree, gh auth status passes. If a release PR for this version is already open, kiln continues from it.
  2. Collect and versionkiln release plan --json reads the squash commits since the last v* tag, applies the bump rules below in code, and returns the version, the rule it used and the grouped commits. Each subject is already a gitmoji PR title with (#N). /kiln-release 2.0.0 passes --version, and /kiln-release --pre rc cuts 1.4.0-rc.1. Exit 3 (the tag exists, or nothing releasable merged) stops the run.
  3. ChangelogIn a release worktree, writes ## [1.4.0] - <date> below ## [Unreleased] in Keep a Changelog form, edits only the wording for readers, rewrites the compare links, and bumps any version_files from config.
  4. Release PRCommits 🔖 chore(release): v1.4.0 on kiln/release-v1.4.0 and opens a ready PR with no Closes #N. kiln ready treats a kiln/ branch with no issue number as a housekeeping PR, so CI is its only gate. kiln-watch takes it to green.
  5. Logkiln-log writes tasks/release-v1.4.0.md on the release branch and pushes it now, because kiln merge deletes that branch.
  6. ◆ Release gateShows the version, the changelog section, CI and the publish route, then waits for a yes. This happens in every autonomy mode.
  7. Merge and tagkiln merge squash merges and returns the merge SHA. kiln tags that SHA with git tag -a, checks the tag points at it, and pushes only that tag. It never force-pushes.
  8. PublishIf a workflow runs on tag push, kiln watches it and reads back the release. Otherwise it runs gh release create --verify-tag with the changelog section as notes, adding --prerelease for --pre versions.

Bump rules

CommitBumpSection
💥 breakingmajor · minor before 1.0Changed, marked BREAKING
✨ featminorAdded
🐛 fix · 🚑️ hotfixpatchFixed
⚡️ perf · ⬆️ deps · ♻️ refactorpatchChanged, kept only when users can see it

🔒️ securitypatchSecurity
🔧 ✅ 📝 👷 🎨 🔖noneleft out

The highest bump wins. A ! after the type or a BREAKING CHANGE footer counts as 💥. The first release is 0.1.0 unless you pass --version.

One writer for CHANGELOG.md

Only kiln-release writes the changelog. If every PR appended to [Unreleased], parallel worktrees would conflict on the same lines. The squash titles on main already hold the record, so the notes are written once, at release time.

A tag is permanent

Kiln tags only the merge_sha that kiln merge returns, with an annotated v tag, and pushes only that tag. It never moves, deletes or force-pushes a tag, and never runs git push --tags. If the push is rejected because the tag exists, it stops and reports.

§12 · Install layout

kiln init, then fire

One Go binary with every skill embedded. Install it with brew install pavelsimo/tap/kiln, go install github.com/pavelsimo/kiln@latest, or a binary from GitHub Releases. In your repo, kiln init writes .kiln/, links the skills into each agent's folder, and prepares GitHub. Re-running it is safe.

  1. PreflightFinds the repo root. Unless you pass --no-github, it needs a GitHub remote named origin and a logged-in gh.
  2. Write .kiln/Writes the skills from the embedded files, config.yaml, the memory skeleton, the verify/ skeleton with evidence/ gitignored, and kiln.lock with a sha256 for every installed skill file. Config, memory and verify are written once and never overwritten, even with --force.
  3. Link agentsDetects Claude Code (.claude/ or CLAUDE.md), Codex (.agents/, AGENTS.md or .codex/) and Cursor (.cursor/ or .cursorrules), or takes --agents. With no signal it links all three. Each skill folder gets a relative symlink, with a copy as the fallback on Windows without symlink rights.
  4. Pointer blockAdds a marked block to AGENTS.md, and to CLAUDE.md when Claude Code is linked, that tells any agent to start at .kiln/skills/kiln/SKILL.md. Everything outside the markers stays yours.
  5. GitHubRuns gh label create --force for 14 labels, and writes the issue template, PR template and ci.yml without overwriting existing files. If you already have a PR template, kiln leaves it alone. --no-github skips the labels but still writes the files.
  6. Hand offPrints next: run /kiln-onboard in your agent. Onboarding fills in PROJECT.md and builds the app driver. Both need to read code, so they're skills, not part of init.

kiln init [--agents claude,codex,cursor] [--no-github] [--force] [-n]

Installs everything above. Safe to re-run: existing files are left alone. --force replaces skills and GitHub templates, but never your config, memory or verify files. -n (--dry-run) shows what would change.

kiln update [-n]

Upgrades skills from a newer binary. Files whose hash still matches kiln.lock are replaced. Files you edited are kept, and the new version is written next to them as <file>.kiln-new for you to merge. New skills are linked, removed ones unlinked, and the pointer block refreshed.

kiln doctor [--no-github]

Checks git, the GitHub remote, gh auth, labels, the config, installed skills against kiln.lock, agent links, the worktree folder, standing checks, and whether the verify driver has fallen behind the code. Exits 3 when something needs fixing; warnings don't change the exit code.

kiln status · checks · verdict · ready · release plan [--json]

Read-only questions with exact answers, for you and for skills (§5). Same input, same output, no model.

kiln move <issue> <state> · kiln merge <pr>

The two guarded writes. move only follows the label state machine. merge squash merges only when kiln ready passes, pinned to the head it checked, then reads the result back and cleans up. Every flag is in the CLI reference.

§14 · Where the ideas come from

Built on pstack's ideas

Many of kiln's best ideas come from pstack, Cursor's plugin for coding agents: one router with playbooks, review backed by evidence, and proving a change on the real surface. Kiln adapts those ideas into its own kiln-* skills and ships them inside the binary, so it never needs pstack at runtime. Where kiln differs, it's because kiln is built around GitHub issues and memory that lives in your repo. Thanks to the pstack authors for sharing their work.

Borrowed adapted from pstack

  • Router and playbooks. One entry skill; action skills are explicit tools.
  • Steps copied into the todo list, with skip: <reason>.
  • Prove rules: predicates, the evidence ladder, the test audit, three verdicts.
  • App driver and feature map, kept honest by a source-and-live maintain pass.
  • Proof-backed findings for large reviews, and merge-time verifiers at the head SHA with the patch-id rule.
  • Worktree per task, ready PRs, and reading back the merge state.
  • Watch order: conflicts, then threads, then CI, with one retry.
  • Lesson confidence: candidate, recurring, strong.

Kiln's own what kiln adds

  • Issue-first. Every task starts as a GitHub issue with acceptance criteria, agreed at gate 1.
  • Memory in the repo, committed with the work and reviewed in PR diffs.
  • Works with several agents through symlinks into each agent's skills folder.
  • Rigor tiered by size, so small fixes stay cheap.
  • A label state machine and fixed branch names.
  • A Go binary that installs everything and answers facts over gh and git.
  • The driver lives in .kiln/verify/ as project memory.
  • Releases from gitmoji squash commits, with one writer for the changelog.
