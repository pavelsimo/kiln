Chapter 01

The idea in one minute

You give kiln a task in plain words, and it handles it the way a careful teammate would.

It writes the task down as a GitHub issue. It makes a plan and shows it to you. It builds the change on its own branch, checks its own work, opens a pull request, gets it green, merges it, and writes down anything worth remembering for next time.

Kiln isn't a new agent, though. It comes in two parts, and it helps to know which is which:

The kiln binaryfacts

A small command line tool. It installs everything, and it answers questions that have exact answers by reading git and GitHub: what's in flight, is CI green, can this PR merge, what's the next version. No AI involved, so it gives the same answer every time.

The skillsjudgment

Instructions the agent you already use follows, for anything that needs thinking: writing the issue, planning, building, proving the change works, reviewing. When a skill needs a fact, it asks the binary instead of guessing.

Your agent still does the work. Kiln gives it a routine, a place to keep notes, and a source of facts it can't argue with. Throughout this tutorial, lines starting with /kiln run inside your agent, and plain kiln … commands run in a terminal.

That routine has six stages. They're named after the way a potter fires clay, which is where the name comes from: the temperature climbs, holds, and then cools slowly so nothing cracks.

GatherYour sentence becomes an issue.
ShapeKiln reads the code and plans.
FireIt builds, test first.
GlazeIt verifies and reviews.
ShipPR, green checks, merge.
TemperIt writes down what it learned.

Two moments in there belong to you. Kiln stops before it writes any code, so you can look at the plan, and before it merges, so you can look at the result. Everything in between runs on its own.

gate 1 · the plan gate 2 · the merge

You can change how often kiln stops later on (that's chapter 8), but this is where everyone starts, and it's a pretty comfortable place to stay.

Chapter 02

Install it

Kiln ships as a single binary with every skill baked in. From the root of your repo, run one command.

That's it for setup. Here's what just happened, in plain terms:

In your repo.kiln/

The skills, a config.yaml with sensible defaults, memory/ and verify/ skeletons, and kiln.lock, which remembers a fingerprint of every skill file so updates can be careful later.

For your agentssymlinks

Each skill is linked into .claude/skills, .agents/skills and .cursor/skills. One copy of the truth, every agent reads it. Pass --agents claude,codex to pick which ones.

On GitHublabels · templates · CI

Fourteen labels that kiln uses to track where each issue is, plus an issue template, a PR template, and a starter CI workflow in .github/. No GitHub remote yet? --no-github writes the files and skips the labels.

A signpostAGENTS.md · CLAUDE.md

A small marked block telling any agent that opens your repo to start with kiln's router. Everything outside the markers is yours.

Kiln is polite about your existing files. If you already have a ci.yml or a PR template, it leaves them alone unless you pass --force, and even --force never touches your config, memory or verify files. Running kiln init a second time is harmless, so if you're ever unsure whether it finished, just run it again. Add --dry-run to see what it would do first.

If something seems off, kiln doctor checks the whole setup and tells you what to fix:

Tip

Got your own skills in .claude/skills/ already? They stay exactly where they are. Kiln links one folder per skill, so it sits next to yours instead of replacing the whole directory.

It works the other way too: kiln never relies on any skill it didn't install. Everything it runs comes out of that one binary, so it behaves the same on a fresh machine as on yours.

Chapter 03

Introduce kiln to your repo

Kiln now knows how to work. It doesn't know your project yet. That's the one thing you do once, from inside your agent.

Kiln looks for the real commands your project uses, the ones CI actually runs, and runs each one once on a clean checkout rather than guessing. Then it writes them into a file called PROJECT.md:

PROJECT.md · .kiln/memory/
# acme/app
Written by kiln-onboard. Edited only via kiln-retro PRs.
## Stack
TypeScript · React 19 · Vite · pnpm · Vitest · Playwright
## Commands
test:      pnpm test
lint:      pnpm lint
typecheck: pnpm tsc --noEmit
build:     pnpm build
e2e:       pnpm test:e2e
## Conventions
- components in src/features/<area>/, one folder per feature
- no default exports
## Do not touch without asking
- src/billing/**   · payments, needs human review
- .github/workflows/release.yml

Please read this file. It takes two minutes, and it's the most valuable two minutes of the whole setup. Every skill reads it. If the test command in here is wrong, every check kiln runs later will be wrong in the same way.

The part worth slowing down for is Do not touch without asking. Onboarding proposes a few candidates and asks you once to confirm, trim or add. Anything listed there, kiln will stop and check with you before editing, in every autonomy mode. Payments, auth, release workflows, that one module nobody fully understands: put them here.

Onboarding does one more thing, and it's a big one. It teaches kiln how to actually run your app. The kiln-verifier skill works out how to start it, how to tell it's ready, how to click through it (or call it, for an API, or run it, for a CLI), and how to shut it down cleanly. It writes all that into .kiln/verify/DRIVER.md, plus three to five short files in features/ describing how a user reaches each area.

Then, before handing it over, it runs the whole thing once for real. A driver that has never been run is just a guess, so you get one that's already been proven. You'll see why this matters in the next chapter, when kiln checks its own work.

All of it lands as one pull request on a kiln/onboard branch. Review it like any other PR. It has no issue behind it, so kiln ready gates it on CI alone, and kiln always waits for your yes before merging it, whatever the autonomy mode. After that, kiln only changes PROJECT.md through retro PRs (chapter 11), though you can edit it like any other file.

Chapter 04

Your first task

Time for the fun part. Let's add dark mode to the settings page and follow it all the way to main.

Hand it a sentence

Gather
Shape
Fire
Glaze
Ship
Temper

Before kiln does anything at all, it tells you what it thinks you asked for. Read that goal line. If it's off, say so now, because this is the cheapest moment there will ever be to correct it.

Next it sizes the work. M means it'll touch several parts of the code, so the checking later will be done by a separate checker and reviewer with fresh eyes. Small tasks get a lighter check, large ones a much heavier one. Then it picks a playbook, which is the recipe for this kind of task, and copies its steps into the agent's todo list word for word. Nothing on that list can quietly disappear. See step 13? It only applies to size L, so kiln rewrote it as a skip with a reason instead of deleting it. You'll see why that matters in chapter 7.

The first step, kiln-recall, reads the project's memory for anything related. On a brand new install there's not much there yet. A month from now, this is where kiln remembers that the settings mock lives in a weird folder, or that visual snapshots need refreshing after any color change.

Then it opens the issue:

✨ add dark mode to settings #42
type:featuresize:Mkiln:ready
Problem

Settings only has a light theme. Several users have asked for a dark one.

Acceptance criteria
  • P1 · a toggle in Settings → Appearance switches the page to dark
  • P2 · the choice survives a reload
  • P3 · a first visit follows the OS theme
  • P4 · must not change: the light theme looks exactly as before
Out of scope

Other pages. They can pick up the theme in a follow-up.

Those acceptance criteria are the contract. Notice how they're written: each one is something you could watch happen or not happen. Kiln calls them predicates and numbers them, because at the end it has to prove every single one before it's allowed to call the task done. "Settings looks nicer" would never make this list. Kiln would rewrite it into something checkable, or ask you.

Look at P4 too. Kiln always adds at least one thing that must not change, because breaking what already worked is the classic way a feature that looks finished goes wrong.

Tip

If you'd typed something vague, like /kiln "make settings nicer", kiln wouldn't invent criteria for you. It switches into interview mode and asks up to five questions in one go. Rough ideas are welcome. They just take an extra minute.

So what should you actually look for at this gate? Three things, really:

  • Is this how you'd do it? If the approach surprises you, ask why. Sometimes kiln knows something you don't. Sometimes it's just wrong.
  • Are these the files you expected? A file you didn't expect is usually the most interesting line in the plan.
  • Do you believe the checks? If the predicates or tests would pass even with a broken feature, say so. This is the last cheap moment to change what "done" means. After this gate, predicates are never loosened to make something pass.

You don't need special syntax. Talk to it the way you'd leave a comment on a colleague's PR. And because the plan lives on the issue (every revision as its own comment), your teammates can see it and chime in too.

Notice where the work happens: ../app.kiln/42-dark-mode-settings. That's a separate git worktree, a second checkout sitting right next to your repo, on a fresh branch cut from origin/main. Your own checkout isn't touched, so you can keep working in it while kiln builds. No stashing, no switching branches under your feet.

Kiln builds test first: a test that fails for the right reason, the smallest change that makes it pass, then a tidy up. Each loop ends in a small commit with a gitmoji and a plain message, and it always stages files by name. It never sweeps up everything with git add -A, so stray files stay out of your history. It also never adds AI attribution or co-author trailers. The commits are yours.

This is the part of kiln most worth trusting, so let's slow down.

Green tests are just the start. Kiln then goes through the predicates one by one and checks each on the real thing it describes. P1 is about something you see on screen, so kiln starts your app with the driver it built during onboarding, clicks the actual toggle, and takes a screenshot. A unit test for the toggle component wouldn't count here. It could pass while the real page stays light.

Each predicate also says how strong its evidence is, on a five step ladder: (1) someone said so, (2) here's the line of code, (3) here's the reasoning, (4) a test ran the real code, (5) we watched it happen in the running app. Only 4 and 5 count as proof. Anything you can see on screen or call over HTTP needs a 5 at this size.

Kiln also audits the tests it leans on. See that rejected test? It only checked that something wasn't empty, so it would have passed even if the feature returned garbage. Kiln won't count it as evidence, and it tells you so you can fix it.

Every predicate ends up with one of three verdicts: VERIFIED, NOT VERIFIED, or INCONCLUSIVE, which means "I couldn't check this", maybe because a test account was missing. The overall verdict is the weakest of the lot, and kiln never rounds INCONCLUSIVE up to a pass.

For an M task, the checking is done by a fresh agent that only gets the predicates, the diff, the commit and the driver. It never saw the build conversation, so it can't be talked into anything. The code review works the same way, with a reviewer that only sees the diff, the issue and PROJECT.md.

Both results are tied to a commit. The report goes into the task's journal, and then kiln asks the binary whether it's on record. That's the kiln verdict call above. --only verify judges just the verify result, since the review hasn't run yet. And same-tree means the only thing that changed since a1c9e0f is the journal commit itself, which the binary ignores, so the verdict still holds.

If a predicate comes back NOT VERIFIED or the reviewer says FIX, the work goes back to the Fire stage and loops: build, commit, verify, review. On the third loop for the same problem, kiln stops and asks you. It all shows up in the task's journal, but you don't have to do anything.

Take a quick look at that first line in the gate. Kiln squash merges, so the PR title becomes the one commit that lands on main, with the PR number on the end. If the title reads well, your history will too.

Every fact in that gate comes from the binary's kiln ready, which reads it straight from GitHub and your git history. You can ask it yourself from any terminal:

The merge itself goes through kiln merge, which runs those same checks and flatly refuses (exit code 3) if anything is red or the verdict belongs to an older commit. It also pins the merge to the exact head commit it just checked, so a push that lands a second later can't sneak in. So even an agent that's very sure of itself can't merge a broken PR.

Kiln also doesn't take the merge on faith. After merging, it reads the PR back from GitHub and only says "merged" once GitHub agrees. Then it cleans up: the kiln:* label comes off the closed issue, and the worktree (only if it has no local changes) and both branches go away. Pass --no-cleanup if you'd rather keep them.

Chapter 05

Reading the trail

Everything kiln did is somewhere you already look. There's no dashboard to learn and no hidden database.

Kiln keeps a simple rule: files record why, GitHub records where. Anything that changes by itself, like CI status, labels or whether a PR is merged, is read live from GitHub every time. Anything that explains reasoning gets written to a file in your repo. That way the notes can't go stale, because they never try to track things that move.

On GitHubwhere things are

  • #42the issue, with the plan as a comment
  • #57the PR, its review and checks
  • labelswhich stage every issue is in

In .kiln/memorywhy things happened

  • tasks/42-dark-mode-settings.mdthe journal
  • decisions/…css-tokens.mda decision record
  • lessons.mdwhat kiln has learned
  • ../verify/how to run your app

The journal is the one you'll open most. It's a short, readable log of who did what:

tasks/42-dark-mode-settings.md · journal
| ts               | skill       | action               | ref     | result   |
| 2026-10-27 14:02 | kiln-issue  | opened issue         | #42     | ok       |
| 2026-10-27 14:09 | kiln-plan   | posted plan          | #42     | approved |
| 2026-10-27 14:31 | kiln-build  | 3 commits, 11 tests  | a1c9e0f | ok       |
| 2026-10-27 14:37 | kiln-verify | 4 predicates · fresh | a1c9e0f | VERIFIED |
| 2026-10-27 14:40 | kiln-review | reviewer subagent    | 7e3a9b2 | PASS     |
| 2026-10-27 14:42 | kiln-pr     | opened PR            | #57     | ok       |
| 2026-10-27 14:58 | kiln-watch  | 0 threads, 0 retries | #57     | ready    |

## Decisions
- CSS custom properties over a theme context → decisions/2026-10-27-css-tokens.md

## Skipped
- skip: kiln-verify swarm · size M, verdict from step 9 covers it

## Retro notes
- every visual snapshot changed after the token move; needed pnpm test:e2e --update

Those verify and review rows matter to the binary too. kiln verdict and kiln ready read the latest one of each, and check whether its commit still matches the branch.

The decision record is the bit future you will thank present kiln for. Six months from now, when someone asks "why didn't we just use a React context for theming?", the answer is a file with a date on it, linked from the issue that caused it.

Labels tell you where everything is

Every open issue kiln is working on carries one kiln: label, and skills move it forward through kiln move, which refuses any jump the state machine doesn't allow (exit code 3). You, your teammates, or a different agent can all see where things stand on GitHub without asking kiln anything.

kiln:needs-triage→ kiln:ready→ kiln:planned→ kiln:in-progress→ kiln:review→ closed

When the PR merges, the issue closes and kiln merge takes the last label off. If something gets stuck, the issue gets kiln:blocked with a comment explaining why and recording where it came from. Once it's unblocked, it goes back to exactly that state.

Chapter 06

A bug, the quick way

Not every task deserves the full ceremony. Let's fix something small and see how kiln scales itself down.

Look at step 4. There's no plan to approve at all. For a size S bug, the bug playbook skips kiln-plan, and with it gate 1, and writes down why: the reproduction test is the plan. The first time kiln stops for you is the merge. If the bug turns out to be size M or bigger, the plan and its gate come back.

Kiln opens #43 🐛 fix login loop after session expiry, with the repro steps, what you expected and what actually happened. Then the bug playbook's one big rule kicks in. The failing test lands before the fix:

Read in order, those two commits prove the bug existed, and prove this change is what fixed it. If someone ever reverts the fix by accident, that test will catch it.

Kiln goes one step further when it verifies a bug fix. It checks out the old code in a throwaway worktree and makes the bug happen twice in the real app, then sees it gone twice on the new code. Twice, because once can be a fluke. It also has to name the root cause at a specific line:

If the fix had only papered over the symptom (say, a retry or a swallowed error), kiln would mark it NOT VERIFIED even with every test green. And if it couldn't make the bug happen on the old code at all, the verdict is INCONCLUSIVE: you can't prove you fixed something you never saw break.

Because it's size S, the author does the verifying and the review is a self-review checklist rather than a separate reviewer. It's still real (the predicates, tests, lint, CI and the checklist all have to pass), it's just proportionate. And if kiln-recall found an earlier bug of the same kind, the journal gets a retro note naming both issues, which is how the next retro spots a pattern.

Chapter 07

Chores, and the skip list

Dependency bumps, config tweaks, docs fixes. Kiln handles these with the chore playbook, and this is a good place to see how kiln skips things honestly.

See that line with the cross? There's nothing to design in a version bump, so kiln skipped the plan. But it didn't just quietly drop the step. It rewrote it as skip: <skill> · <reason>, right there in the list, and the same line goes into the journal under ## Skipped.

This is a small thing that turns out to matter a lot. When you look back at any run, the todo list tells you exactly what happened and what didn't, and why. A step can never just vanish. If you ever find yourself wondering "did it run the tests?", the answer is in the list.

Light doesn't mean skipped, either. Step 7 still produces a real verdict, with short predicates like "pnpm lint exits 0" plus any standing checks that match the change. And if a chore turns out to change behavior, it isn't a chore anymore: kiln stops, tells you, and re-routes it as a feature or a bug.

You can ask for skips too ("skip the plan, it's a one line change") and kiln will write your words down as the reason. The one exception is size L work. Big tasks always need a human to look at the plan, so that gate never gets skipped.

Chapter 08

Giving kiln more rope

So far kiln has stopped at every gate that applied. That's the gated mode, and it's the default. There are two others.

manual

Kiln runs one skill, tells you what happened, and suggests the next step. Nothing chains on its own.

stops after every stepNice for your first day, if you want to watch closely.

gated default

Kiln runs the whole playbook and waits for you only before writing code and before merging.

◆1 plan · ◆2 mergeWhere most people live, most of the time.

autopilot

Kiln goes from sentence to merged PR, as long as kiln ready says yes: every predicate VERIFIED, CI green and the review clean.

◆1 for size L onlyFor when the plans have been boring for a while.

Switching is one line in .kiln/config.yaml:

config.yaml · .kiln/
# How often kiln stops for you: manual | gated | autopilot
autonomy: gated
# The gates used when autonomy is gated
gates: [plan, merge]

# How hard kiln checks its own work, by size label
rigor:
  S: { verify: self, review: self }
  M: { verify: fresh, review: independent }
  L: { verify: swarm, review: adversarial, force_gates: [plan] }

Notice the two settings are separate. autonomy decides how often kiln stops for you. The task's size decides how hard kiln checks its own work. Turning up autonomy doesn't lower the bar on review. In autopilot, an M task still needs a fresh checker to say VERIFIED and an independent reviewer to say PASS, both still valid for the exact commit being merged. Size L goes further: right before merging, three independent checkers rerun every gate, prove the key behavior live in the app, and audit the diff and the evidence.

And one rule holds in every mode: INCONCLUSIVE never merges on its own. In gated mode you'll see it at the merge gate and can accept it if you know why. Autopilot simply stops and asks.

Things kiln always asks about

No matter what mode you're in, some actions always stop and wait for a human. These aren't settings, so you can't turn them off by accident:

force-push to a shared branch delete unmerged work or data deploy, release or tag merge with failing checks change secrets or repo settings message people outside the repo edit a "Do not touch" path
Our suggestion

Spend a week on gated. If you notice you're approving plans without changing anything, that's your cue to try autopilot. You'll still see every PR, big tasks still wait for you at the plan, and you can always flip it back.

Each worktree only ever writes its own task journal, which is why three tasks can run side by side without their notes ever conflicting at merge time.

Picking up where you left off

Closed your laptop halfway through a build? Your agent restarted? Nothing is lost. The next morning:

Kiln trusts the journal over its own guesses. It rebuilds the todo list from the playbook, checks the journal against the branch, the PR and kiln verdict, and carries on from the first step that isn't done. Uncommitted work is kept, never thrown away to "start clean".

Chapter 11

Letting kiln learn

Remember those "retro notes queued" lines? Every so often, kiln turns them into something useful.

The retro reads recent journals and looks for friction that keeps coming back: the same test failing for the same silly reason, the same file that's always forgotten, the same step that keeps getting skipped. Then it proposes changes, all in one PR:

lessons.md · PR #60
- [recurring] Run `pnpm test:e2e --update` after any token change.
+ [strong] Run `pnpm test:e2e --update` after any token
+   change; visual snapshots fail otherwise. (#31, #42, #49)
  [recurring] The `settings` API mock lives in test/fixtures,
    not __mocks__. (#31, #42)
+ [candidate] CI's Node 20 job is flaky on the websocket test.
+   Retry once before treating it as real. (#47)

Each lesson carries a confidence level. A candidate has been seen once. A recurring one has shown up in two or three tasks. A strong one has earned its place as a rule, and kiln's planner, builder and reviewer treat it that way. The issue numbers at the end show where each one came from, so you can always check its reasoning.

You review this PR like any other. If a lesson is wrong, delete the line. Nothing about kiln's memory ever changes behind your back: only the retro writes lessons, it always goes through a pull request, and kiln waits for your yes before merging it, even on autopilot. Sometimes it'll propose a change to PROJECT.md, an edit to one of kiln's own skills, or turn a strong lesson into a standing check (that's the next chapter), and those land in the same PR.

Lessons and who writes what

Chapter 12

Teach kiln your own checks

Every project has rules that live in somebody's head. "Migrations must roll back." "No raw hex colors." Kiln can hold those too.

They're called standing checks, and they live in one small file:

checks.yaml · .kiln/verify/
- id: migrations-reversible
  when: { paths: ["db/migrations/**"] }
  predicate: pnpm db:rollback && pnpm db:migrate both exit 0
  blocking: true
  from: .github/workflows/ci.yml · job migrations

- id: tokens-only
  when: { paths: ["src/**/*.css", "src/**/*.tsx"] }
  predicate: pnpm lint:tokens exits 0
  blocking: true
  from: lessons.md · strong · #31 #42 #49

Each check says which files it cares about (and, if you like, which issue labels) and what has to be true. Whenever a branch touches those files, the check joins that task's predicates, right next to the acceptance criteria, and gets proven the same way. A blocking check counts toward the overall verdict. Anything else is reported as advisory.

Working out which checks apply is a plain fact (which files changed?), so the binary does it, and you can ask it yourself:

Proving them is judgment (does the rollback really leave the schema untouched?), so that part is kiln-verify's job. Facts in code, judgment in skills. You'll notice that pattern everywhere in kiln.

Where checks come from

Onboarding seeds the path-scoped ones your CI already runs, like that migrations job (zero is fine too). You can add your own any time. And the retro graduates them: when a lesson reaches strong and it's something that can be checked, the retro PR proposes turning it into a standing check, after running it once to make sure it's green on main. See the from: line above. That one is the token lesson the retro promoted to strong back in chapter 11.

The difference matters. A lesson is something kiln remembers. A check is something kiln can't forget.

Keeping the driver honest

Your app keeps changing, and the driver from chapter 3 can slowly drift out of date. Each feature file lists the source files behind it, so the binary can count how many commits have touched them since the driver last changed:

When that happens, the next retro runs kiln-verifier maintain. It reads the code behind every feature, then drives every feature live, even the ones that look fine on paper. Anything that doesn't match gets sorted out: the map was wrong, the driver couldn't reach something, the app itself is broken, or a feature needs something kiln can't get (like a paid account). Fixes to the map ride along in the retro PR.

Heads up

Kiln only ever fixes the map, never your app. If a feature is actually broken, you get a bug issue with the commands and output it saw, and the driver stays as it was. Kiln never rewrites the map to match broken behavior.

Chapter 13

Cutting a release

It's Friday, a bunch of good stuff has landed on main, and you'd like to ship it. Releases work a little differently from tasks, because they gather up many tasks at once.

Working out the next version is pure arithmetic over your commit history, so the binary does it. You can ask it any time. It's read-only, so nothing gets written, tagged or published:

It shows its reasoning on the rule line. Since every squash commit on main starts with a gitmoji, it can tell what kind of change each one was: a 💥 means major, a ✨ means minor, a 🐛 means patch, ⬆️ ♻️ and ⚡️ are patches under Changed, and housekeeping like 🔧, ✅ or 📝 is left out entirely. The biggest bump wins. If nothing releasable has merged since the last tag, or the tag already exists, it says so and exits 3.

The /kiln-release skill takes it from there:

The version is the binary's answer, and the skill only edits the wording of the notes so they read well for users. Notice the eslint bump is gone: nobody using your app can see it. Disagree with the number? Just say so. /kiln-release 2.0.0 sets it yourself, and /kiln-release --pre rc gives you 1.4.0-rc.1 for a release candidate. Either way the skill passes it to kiln release plan rather than editing the number by hand.

Notice the changelog goes through a normal PR, #61, with CI and everything. It has no issue behind it, so kiln ready treats it as a housekeeping PR and CI is the only gate. Until you say yes at the gate, nothing is permanent. Closing that PR undoes the whole release. After you say yes, kiln merges with kiln merge, tags the merge commit, and publishes, either by watching your tag workflow or by creating the GitHub release itself.

Heads up

The release gate stops in every autonomy mode, autopilot included. Releasing is one of those things kiln always asks about.

And if a release goes out broken, the fix is v1.4.1. Kiln will never move or delete a tag that's already public, because someone may already have pulled it.

One last detail you might wonder about: why doesn't each PR add its own line to CHANGELOG.md as it merges? Because three tasks running side by side would all edit the same lines and conflict. The squash titles on main already hold the whole story, so kiln writes the changelog once, at release time.

Chapter 14

Keeping kiln current

Kiln's skills are files in your repo, which means they're yours. Edit them as much as you like. Updates are designed around that.

Upgrade the binary the same way you installed it, then preview what it would change:

Remember kiln.lock from the install? It holds a fingerprint of every skill file kiln wrote. When you update, any file that still matches its fingerprint is simply replaced with the new version. Any file you've changed is left exactly as it is, and the new version is written next to it as SKILL.md.kiln-new so you can merge the two at your own pace. Until you do, kiln doctor reminds you that it's there.

Update also links any new skills into your agents, unlinks ones kiln no longer ships, and refreshes the signpost block in AGENTS.md and CLAUDE.md. Your customizations never get silently overwritten, and you never miss an improvement either. Your config.yaml and the files in .kiln/verify/ and .kiln/memory/ are yours from day one, so updates don't touch them at all. Neither are your own skills, the ones that were in .claude/skills/ before kiln arrived.

Chapter 15

When things feel off

A few questions that tend to come up in the first couple of weeks.

Kiln stopped and I'm not sure why.

Run kiln status or /kiln-status. Anything waiting on you shows up with a ◆ next to it. If the task isn't waiting on you, open its journal in .kiln/memory/tasks/: the last row says what kiln did most recently and how it went. A blocked issue will also have a comment on GitHub explaining what's in the way.

What do kiln's exit codes mean?

Every command uses the same four. 0 means ok, or yes. 1 means something failed underneath, like git or gh. 2 means the command was called wrong, like an unknown flag or a missing argument. 3 means the answer is no: the PR isn't ready, the verdict is stale, the label move isn't allowed, the merge was refused, doctor found a problem, or there's nothing to release.

Skills treat a 3 as an answer to follow, never something to work around. That's what makes kiln ready and kiln merge safe to hand to an agent.

kiln-verify says INCONCLUSIVE. Is that bad?

It's honest. It means kiln couldn't check that predicate, and the report says why and what would unblock it: a missing test account, a service it can't reach, a bug it couldn't reproduce on the old code. Fix the gap (often something /kiln-verifier can add to the driver) and run /kiln-verify again, or accept it at the merge gate if you know it's fine. Kiln only passes --accept-inconclusive after you say so, and autopilot never merges past it on its own.

My app is a CLI (or an API). Does the driver still work?

Yes. The driver describes whatever "using the app" means for your project: clicking through pages, calling endpoints with curl, or running commands and keeping their output and exit codes. Onboarding works out which one you have.

Can I skip the plan just this once?

For small work, sure. Tell kiln, and it records skip: kiln-plan with your words as the reason, in the todo list and the journal. Features can waive it at size S, and small bugs and most chores skip it on their own. Refactors never do, because the order of the steps is the whole safety story. And size L tasks always need a human at the plan, in every mode.

CI failed on something that has nothing to do with my change.

kiln-watch sorts CI failures into real and flaky, and it retries a flaky job once. If it fails a second time, kiln treats it as real, moves the issue to kiln:blocked with the reason, and tells you. It also leaves a retro note, so if the same flaky test keeps showing up, the next retro will usually suggest a lesson about it.

What if two tasks change the same file?

They each build in their own worktree, so they don't interfere while they're working. Whichever one merges second will hit a conflict, and resolving conflicts is the very first thing kiln-watch does before looking at reviews or CI. A clean rebase keeps the verdict fresh (the change has the same git patch-id). If resolving the conflict changed the code, kiln verifies and reviews again. If it can't resolve something confidently, it asks you.

I edited a skill and now kiln update left a .kiln-new file.

That's working as intended. Compare the two, keep what you want in SKILL.md, then delete the .kiln-new file and kiln doctor stops reminding you. Kiln has already recorded the new version in kiln.lock, so from then on your file counts as your edit, and updates leave it alone until kiln ships another change to it.

Do I need any other skill packs installed?

No. Kiln ships its own version of everything inside the binary and never calls a skill or tool it didn't install. A fresh machine with just kiln, git and gh (plus your agent) is enough.

Does this only work with Claude?

No. The skills live once in .kiln/skills/ and are linked into Claude Code, Codex and Cursor. Memory is plain files in git, so you can start a task in one agent and resume it in another. Kiln doesn't read any agent's private transcripts.

I just want to see what's in the backlog.

kiln status shows the counts, and every kiln issue is a normal GitHub issue with normal labels. gh issue list --label kiln:ready works just as well, and so does the GitHub website.
